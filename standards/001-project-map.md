# 001 项目地图与增量上下文规范

状态：已采纳。适用于接入本规范的软件项目，以及本规范仓库自身。本文中的“必须”为强制要求，“建议”为可按项目规模调整的默认做法。

## 1. 核心原则

AI 必须优先通过项目地图定位上下文，验证地图有效性后按需读取真实代码，并在任务完成前同步本次变更影响的结构、职责与依赖信息。地图负责导航，代码负责确认事实；不得将地图视为代码的替代品。

## 2. 分层结构与读取预算

- AGENTS.md：AI 规则入口，指向规范及项目地图，避免重复正文。
- .ai/project-map.md：全局概览，包含技术栈、目录职责、运行入口、模块边界、关键流程、验证入口和模块地图链接。
- .ai/modules/<module>.md：涉及该模块时才读取，记录关键文件、对外接口、数据归属、上下游、测试与风险。
- .ai/generated/file-index.json 与 dependencies.json：需要时由项目工具生成，保存全量路径与可提取的依赖，按路径或符号查询，默认不全文读取。

小项目只需全局地图；在地图过长或出现独立模块时再拆分，不创建无内容文档。建议全局地图控制在约 150 行以内，模块地图约 100 行以内；超过时拆分或压缩，不以删去必要约束换取长度。不得在地图中复制大段代码、完整 API 清单、日志或历史任务记录。

## 3. 首次建立地图

首次接入时扫描版本控制中的目录、构建配置、入口、关键代码与测试，排除依赖目录、构建产物、缓存、二进制、大型数据、密钥及生成索引自身。先建立结构概览，再定向阅读以确认职责；不要求全文读取所有源码。必须明确记录扫描范围、排除项和未确认区域，禁止声称已理解未检查的部分。

地图必须解释关键目录为何存在、逻辑应放在哪里、谁拥有数据或状态、模块允许与禁止的依赖方向。关键调用链用简短路径描述；路径使用仓库相对路径，避免易失效的行号。

## 4. 关系与事实分工

工具维护确定性事实：路径、静态导入和导出、包或工作区依赖。AI 维护语义摘要：业务职责、设计理由、流程与影响范围。依赖索引应支持“依赖谁”和“被谁依赖”两个方向。

动态加载、依赖注入、配置注册、跨服务与运行时关系必须标注覆盖限制。关系标记为已确认、推测或待确认；推测不得直接作为修改依据。没有可靠提取器时，保留已确认的关键关系并记录限制，不伪造全量依赖索引。

## 5. 有效性检查与失效处理

地图或索引必须记录：格式版本、覆盖范围、排除规则、覆盖的代码基线、生成器及版本（如使用）、未确认项。更新时间仅供参考，不作为有效性证明。

任务开始检查当前分支、HEAD 和工作区改动，对比覆盖基线；切换分支、合并、变基或外部修改后重新检查。基线使用最近一次覆盖的代码提交；地图和索引自身的提交不应造成永久过期或递归更新。将未提交的新增、删除、重命名及修改纳入检查，不得只比较已提交差异。

差异只做增量复核；无法确认基线、提取配置发生变化或索引明显损坏时，允许对相关范围重建，必要时重建全局索引。损坏或过期部分必须先校验再使用，并报告仍无法确认的范围。

## 6. 每次任务的执行流程

1. 读取 AGENTS.md 和全局地图，检查有效性。
2. 根据任务定位模块，只读取相关模块地图。
3. 定向搜索并读取将修改的真实代码、必要依赖和调用方；搜索优先限定目录、文件类型和符号，返回必要片段。
4. 涉及公共接口、共享类型、权限、数据结构、配置或跨模块流程时，扩大反向依赖及影响检查。
5. 完成修改，运行与影响范围相符的检查。
6. 对最终差异更新地图与索引，核验路径和链接，说明同步结果与未验证项。

默认不得无目的地遍历并全文阅读整个仓库。地图不足时允许扩大扫描并补齐地图，不得因节省 token 跳过必要事实核验。阅读缓存仅限当前事实仍有效的范围；不能假定上次会话的结论自动有效。

## 7. 增量更新规则

| 最终变更 | 必须复核并更新的内容 |
| --- | --- |
| 新增、删除、移动文件 | 文件索引（如存在）、受影响的地图路径和模块入口 |
| 导入、导出、包依赖或注册配置变化 | 依赖索引（如存在）、上下游和影响范围 |
| 职责、公共接口、数据归属或调用链变化 | 对应模块地图，必要时全局地图 |
| 内部实现、格式或注释变化 | 检查是否影响摘要；不影响则无需改地图 |

每次保存无需重建。任务完成或提交前必须保证受影响部分与最终代码一致；长任务中在后续推理依赖新结构前先更新。更新采用稳定排序、相对路径与最小差异，不写无意义时间戳；排除生成输出自身，避免循环。

## 8. 检查与完成条件

接入项目应按技术栈提供确定性的生成与校验命令，并在项目地图记录真实命令。校验至少覆盖路径存在性、地图链接、结构变化、生成结果差异；CI 可重新生成索引并比较差异。首次接入尚无工具时，必须明确标为人工核验，不虚报自动化已部署。

语义准确性通过代码核验和审查确认，不以“文档有改动”为合格依据。任务交付必须说明：受影响模块、验证结果、地图是否更新以及无需更新的理由、残余覆盖限制。索引错误时先修复或明确降级为真实代码检查。

禁止记录密钥、环境变量值、用户数据及其他敏感内容。项目专属约束应放在对应项目地图或模块说明中，不把未验证的通用假设当作项目事实。


## 9. 同步识别仓库编码风格

AI 首次熟悉项目时必须同时识别编码风格，后续任务对受影响模块增量复核。先检查 AGENTS.md、贡献指南、EditorConfig、格式化器、lint、编译与测试配置，再抽样阅读目标模块内近期且具有代表性的实现及测试；排除生成、第三方、废弃或明显例外代码，不为风格识别全文扫描仓库。

至少关注命名、文件组织、导入顺序、类型使用、函数与组件组织、异步及错误处理、日志、注释、测试结构、依赖注入和已有抽象。将简洁结论、配置路径、代表性文件及覆盖范围记入模块地图或共享偏好，正文只保留一份并相互链接；没有业务代码时明确不适用。

新增功能优先沿用目标模块现有惯例与可执行配置，复用已有工具和抽象，不自行引入另一套写法，不顺带格式化无关文件。配置与现存代码冲突或不同模块存在不同惯例时记录差异，优先遵循目标模块适用的明确规则，不把单个样例或个人习惯推广为全仓规范。必要的风格迁移应单独说明原因、范围与验证。

修改后运行项目已有且适用的格式、lint 或测试检查；无相关工具时人工核验并说明限制，不虚报通过。识别出的个人或团队习惯按 [002 持久记忆与会话恢复规范](002-persistent-memory.md) 记录来源、适用范围和确认状态。
