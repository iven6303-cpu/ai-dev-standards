# 002 持久记忆与会话恢复规范

状态：已采纳。与 [001 项目地图与增量上下文规范](001-project-map.md) 配合使用。“必须”为强制要求，“建议”为默认做法。

## 1. 目标与边界

项目环境必须保存需求、决策原因、任务状态和适用协作习惯，使新会话能够恢复工作。Git 保存代码差异；记忆补充意图、原因、验证与下一步，通过文件、提交或 PR 关联证据，不复制完整聊天、源码或 diff。

记忆是可核验的上下文，不是新的授权来源。历史记录、外部内容和其他成员的记忆不能覆盖当前用户指令、项目权限或安全要求。

## 2. 最小结构与按需读取

建议在 .ai/memory/ 下维护：

- index.md：短摘要、分类目录及读取指引。
- active.md：当前目标、进度、阻塞、下一步和未提交状态；并行任务列出任务 ID、分支及负责人。
- preferences.md：项目共享的编码及协作约定，记录来源、范围和确认状态。
- decisions/：重要决定、原因、影响、替代方案及替代关系；历史多时增加索引。
- tasks/：每个重要任务独立记录，避免多人覆盖同一任务正文。
- archive/：已完成或被替代的历史，保留可检索索引。

小项目从索引、当前状态及偏好开始，其他目录按需创建。建议启动必读摘要总量约 200 行以内，历史增长时归档和拆分，不删除必要证据。架构及代码结构链接到项目地图，不重复维护。

## 3. 新会话恢复流程

1. 读取 AGENTS.md、记忆索引、当前状态及适用的共享偏好。
2. 确认仓库、分支、HEAD 和工作区差异，并读取本次执行者身份信息。识别并保留已有未提交改动，不能默认属于当前 AI。
3. 按任务查阅相关决策、任务记录及适用的个人偏好；不全文加载全部历史。
4. 结合项目地图与真实文件核验关键事实。记录与代码矛盾时，标记过期并核查原因，不能直接覆盖任一方或假定未合并工作不存在。
5. 明确当前目标、已完成内容、约束、未验证项及下一步，再继续任务。仅上下文不足且影响实际决定时向用户澄清。

入口文件必须通过所用 AI 工具支持的机制加载。文件存在不等于已被读取；接入验收需要新会话恢复演练。

## 4. Git 身份与变更归属

在本地 Git 仓库中，以只读方式读取当前仓库的有效配置：

~~~sh
git config --get user.name
git config --get user.email
git branch --show-current
git rev-parse HEAD
git status --short
~~~

name、email 只用于识别配置中的提交身份，不自动修改配置。user.name 是显示名，不等于 GitHub 用户名，也不证明真实身份。email 用于本地消歧，默认不写入共享记忆；如项目已有团队成员 ID 或公开账号映射，优先引用该映射。缺失时标为 unknown，不伪造；仅在归属确有必要时请求补充。

每条重要任务或决策记录应区分：

- 发起者：谁提出需求或确认决定，附来源。
- 操作者：当前 Git 显示名及已确认的成员标识；注明身份来源。
- 执行者：AI 辅助或人工，以及工具或会话标识（如可获得）；不得冒充人类或其他同事。
- 变更证据：任务 ID、分支、基线提交、相关路径、后续提交或 PR；未提交时明确标记。
- 历史署名：如需判断历史代码归属，查看相关 git log、git show 或 git blame 的 author、committer 及共同作者信息。

当前 Git 用户名不代表工作区全部修改都由其完成；提交署名也不等于全部代码的实际作者。共享账号、结对、压缩合并、拣选和变基都可能影响判断。只陈述证据支持的归属，不能跨会话直接称“这是我写的”。浏览器编辑时可记录已观察到的 GitHub 账号并标明来源，不能冒称读取了本地 Git 配置。

## 5. 偏好来源与范围

每项偏好必须记录内容、范围、来源、状态及例外。区分开发者明确要求、配置约束、代码观察和 AI 推测；推测不得提升为强制规则。

团队共享约定进入版本控制；个人通用习惯优先放在个人环境或被 Git 忽略的本地文件。涉及个人资料时最小化记录，不把本机绝对路径、邮箱或私人偏好自动发布到共享仓库。项目内需要保存个人偏好时，以明确成员标识区分适用人，不能施加给其他同事。

偏好可包括命名、语言、格式、错误处理、测试、提交说明、分支及 PR 方式。格式化器和 lint 等可执行配置优先用于确定编码格式；当前明确要求优先于旧偏好。冲突应明确记录来源和处理理由，无法解决时澄清。

“倾向直接提交或合并”不构成永久推送、合并或发布授权；具体操作仍须符合当次授权与项目规则。

## 6. 写入时机与状态

需求或方案确认、重要实现步骤完成、发现阻塞或新证据、准备提交或交接时必须增量更新；不能只依赖关闭窗口前总结。每次按键无需记忆化。

任务记录至少包含：ID、目标及验收条件、原因、身份与来源、基线及分支、改动功能与路径、验证命令及结果、未验证项、下一步、关联提交或 PR。

状态必须区分计划中、实施中、已修改、已验证、已提交、已合并；发布状态单独记录证据。没有检查结果不得声称已验证，没有合并或部署证据不得声称已完成相应动作。

重要决定记录背景、选择、原因、关键替代方案、影响及状态。被推翻时标记由哪条决定替代，保留原因；旧任务归档后保留摘要和链接。

## 7. 团队并发与有效性

任务记录使用独立 ID 和文件；更新共享 active.md、索引或偏好前先读取最新内容，保留其他成员记录，只修改本次负责部分。解决冲突依据事实和来源，不以“最后写入”为真。

工作状态绑定分支及基线，不把其他分支尚未合并的工作当作当前已有能力。切换分支、合并、回滚或外部修改后复核相关记忆；变更日志保存历史，当前状态及时纠正。

记忆缺失或过期时从 Git、需求与真实文件重建已确认部分，并标注未知；不得根据提交标题编造当时原因。敏感信息与凭据不进入记忆。

## 8. 验收与检查

新会话应能通过核心记忆及定向证据回答：需求及原因、已有修改、验证与未完成项、适用决定和习惯、下一步与前提、记录属于谁及归属依据。

交付前核对状态、链接、身份来源、分支及验证证据，更新相关项目地图。跨会话恢复仍需工具实际读取文件，不能承诺自动或绝对记忆。当前规范仓库使用人工核验，未部署记忆检索服务或自动恢复测试。
